# 워크스페이스 전환 — 스태시 창 방식 (재로딩 방지 + 메모리 상한)

## 배경 / 요구사항

- **재로딩 금지**: 저장된 그룹(워크스페이스)으로 전환할 때, 예전에 열려 있던 탭이
  다시 네트워크 로딩되면 안 된다. (예: 1번 그룹 → 2번 그룹 → 다시 1번 그룹으로
  돌아오면 1번 탭들이 재로딩되던 문제)
- **메모리 폭등 금지**: 재로딩을 없애려고 모든 워크스페이스 탭을 살려 두면 워크스페이스가
  쌓일수록 메모리가 무한정 늘어난다. 이건 허용 안 됨.

이 둘은 근본적으로 상충한다(재로딩 방지 = 탭을 살려 둠 = 메모리 사용). 그래서
**"최근에 떠난 워크스페이스 몇 개만 살려 두는" LRU 상한**으로 절충했다.

## 구현 요약 (`src/background/service-worker.js`)

### 스태시 창(stash window)

- 최소화된 백그라운드 창을 **딱 1개** 만들어, 전환해 떠나는 워크스페이스의 탭을
  **닫지 않고 그 창으로 이동(park)** 시킨다. 탭이 살아 있으므로 되돌아올 때 그대로
  다시 옮겨오면 **재로딩 없이** 스크롤·폼·로그인 상태가 보존된다.
- 스태시 창은 영구 `about:blank` "keeper" 탭 1개를 유지해서, 마지막 park된 그룹을
  되돌려 비어도 창이 자동으로 닫히지 않는다(세션 동안 창 id 안정).
- **창은 딱 1개만 재사용한다.** MV3 서비스워커는 유휴 시 죽으므로 메모리의
  `stashWindowId`가 사라지는데, `ensureStashWindow`는 새로 만들기 전에 항상
  `storage.local`에서 창 id를 복구·검증한다. 이 복구가 없으면 워커 재시작 이후
  전환마다 스태시 창이 새로 생겨 **창이 계속 늘어나는 버그**가 난다(수정 완료).
- 스태시 창은 생성/탭 이동 직후 `state:"minimized", focused:false`로 강제해
  앞으로 튀어나오지 않게 하고, 전환 끝에 사용자 창을 다시 포커스한다.
- 상태는 서비스워커 재시작(MV3는 유휴 시 워커가 자주 죽음)에도 살아남도록
  `chrome.storage.local`에 저장:
  - `tabinet.stashWindow` → 스태시 창 windowId
  - `tabinet.stashed` → `{ [groupId]: tabId[] }` (그룹별 park된 탭 id)
  - `tabinet.stashOrder` → 최근 park 순서(LRU 판단용, 최신이 앞)

### LRU 상한으로 메모리 제한

- 상수 **`MAX_STASHED_ALIVE`** (현재 `2`): 스태시 창에 **동시에 살려 두는
  워크스페이스 개수 상한**.
- park할 때 이 그룹을 최신으로 올리고, 상한을 넘은 **가장 오래된 워크스페이스는
  탭을 닫아(메모리 회수)** 버린다. 닫힌 그룹은 다음 전환 때 기존 lazy 방식으로
  다시 열린다(그때만 재로딩).
- 결과: 메모리 = **활성 워크스페이스 + 최대 `MAX_STASHED_ALIVE`개 park 워크스페이스**로
  묶임. 워크스페이스를 아무리 많이 만들어도 메모리는 고정 상한.
- **튜닝**: 재로딩 없는 워크스페이스를 더 원하면 `MAX_STASHED_ALIVE`를 올리고,
  메모리를 더 아끼려면 내린다(1로 두면 "직전 워크스페이스 1개만" 살아 있음).

### 이벤트 격리

- 모든 탭 이벤트 리스너와 `scheduleWorkspaceSync`에 `isStashWindow()` 가드를 넣어,
  스태시 창 내부의 탭 이동/생성/삭제가 라이브 동기화나 "빈 워크스페이스" 처리로
  잘못 이어지지 않게 했다.
- 스태시 창이 닫히면(`windows.onRemoved`) `clearStash()`로 모든 스태시 상태를 폐기.

### 삭제 정리

- 그룹 삭제 시 park된 탭도 닫아야 오펀 탭이 안 남는다.
  - 서비스워커 `REMOVE_GROUP` 경로: `discardStashedGroup()` 호출.
  - 사이드바/에디터는 스토리지 레이어로 **직접** 삭제하므로, 그룹 인덱스
    (`tabinet.order`) 변경을 감지하는 `storage.onChanged` → `reconcileStash()`로
    사라진 그룹의 park 탭을 정리.

## 남은 정리·후속 과제 (TODO / 한계)

1. **브라우저 재시작 시 오펀 스태시 창**
   - 재시작하면 park된 탭 id가 무효화되어 스태시 매핑은 폐기(→ 해당 그룹은 lazy로
     다시 열림)되지만, 크롬 세션 복원이 **최소화된 스태시 창을 그대로 되살리는**
     경우 park돼 있던 탭들이 담긴 창이 유령처럼 남을 수 있다.
   - 현재는 자동 정리하지 않음(오탐 위험 때문에). 후속으로 startup 시
     "최소화 + lazy 플레이스홀더 위주 + keeper about:blank" 특징으로 오펀을
     식별해 닫는 로직을 검토. (활성 워크스페이스 복원 창과 오탐 구분이 관건)

2. **작업표시줄/Alt-Tab 노출**
   - 스태시 창이 최소화 상태로 작업표시줄·Alt-Tab에 1개 나타난다. 사용자가 실수로
     이 창을 포커스/조작하면? → 이벤트 가드로 대부분 무해하지만, UX상 숨길 방법
     (전용 아이콘/타이틀 표시 등) 검토 여지.

3. **park 탭의 실제 메모리**
   - park된 탭은 여전히 크롬 탭 카운트·메모리에 잡힌다(상한 내에서). 다만
     최소화 백그라운드 창이라 크롬 Memory Saver가 시간이 지나면 자체 discard할 수
     있고, 아직 안 본(lazy) 탭은 가벼운 로컬 플레이스홀더라 부담이 작다.
   - 더 공격적으로 줄이려면 `chrome.tabs.discard`를 쓸 수 있으나, discard는
     재활성 시 **재로딩**되고 `onReplaced`로 탭 id가 바뀔 수 있어 매핑 관리가
     복잡해진다. 지금은 "닫기(close) 후 lazy 재개" 방식을 택함(구현 단순 + 명확).

4. **다중 실제 창(멀티 윈도우)**
   - 스태시 창은 전역 1개이고 park 매핑은 `groupId` 기준. 서로 다른 실제 창에서
     같은 그룹을 동시에 활성화하는 시나리오는 가정하지 않음(그룹당 1창 전제).
     멀티 윈도우로 확장한다면 매핑 키에 windowId를 포함할지 재검토 필요.

5. **`MAX_STASHED_ALIVE` 노출**
   - 현재 하드코딩 상수. 필요하면 설정(옵션 페이지)으로 노출해 사용자가
     메모리 vs 재로딩 트레이드오프를 직접 조절하게 할 수 있음.

6. **활성 그룹의 "Reopen" 라벨**
   - `switchToGroup`에 `prevId === id`면 조기 반환(no-op)을 추가했다(같은 그룹으로의
     전환이 자기 탭을 stash+재생성하며 깨지는 것을 막기 위함). 그 결과 사이드바에서
     활성 그룹에 표시되는 **"Reopen" 클릭이 아무 동작도 안 한다.**
   - 후속: 사이드바(`sidepanel.js`)에서 활성 그룹 라벨을 "Reopen" 대신 "Current"
     같은 비활성 표기로 바꾸거나, 정말 강제 새로고침이 필요하면 별도 동작으로 분리.

## 수동 테스트 체크리스트

- [ ] 1번 그룹 열기 → 2번 그룹으로 Open all → 다시 1번으로 Open all:
      **1번 탭들이 재로딩되지 않고** 스크롤/입력 상태가 유지되는가?
- [ ] 3개 이상 워크스페이스를 순회(1→2→3→4…)할 때, `MAX_STASHED_ALIVE`를 넘긴
      오래된 워크스페이스로 돌아가면 lazy로 다시 열리는가(정상), 그리고 최근
      2개는 재로딩 없이 도는가?
- [ ] 워크스페이스를 많이 만들고 순회해도 **메모리가 상한에서 안정**되는가?
      (park 창 탭 수가 keeper + 최대 상한 그룹 합으로 유지)
- [ ] park된 그룹을 사이드바/에디터에서 **삭제**하면 스태시 창의 해당 탭이 닫히는가?
- [ ] 그룹 전환을 여러 번(중간에 30초 이상 쉬어 워커 재시작을 유발) 반복해도
      **스태시 창이 딱 1개만** 유지되고, 전환 때마다 창이 앞으로 튀어나오지 않는가?
- [ ] 스태시 창을 사용자가 수동으로 닫아도 이후 전환이 정상(그룹이 lazy로 열림)인가?
- [ ] 활성 워크스페이스의 탭을 전부 닫았을 때(빈 워크스페이스) 다음 그룹이
      park돼 있으면 재로딩 없이, 없으면 lazy로 열리는가?
- [ ] 서비스워커를 강제로 종료했다가(약 30초 유휴) 다시 전환해도 park 매핑이
      복구되어 동작하는가?
